# 数仓重构项目：数据开发与治理规范手册 (V1.0)

本规范适用于纳入公司数仓体系的正式数据资产，对历史遗留系统与过渡期对象，允许在评估后分阶段纳入。

> **⚠️ 关于本规范的适用范围说明（非目标声明）**
>
> 本规范旨在**统一原则、划定边界与确立最低标准**，**不以覆盖所有技术实现细节为目标**，亦不可替代具体项目的设计文档与实施方案。
>
> * **防止教条主义**：规范未明确禁止的技术方案，在经过架构评审后**允许探索**。
> * **防止手册化**：本规范不是“操作手册”，具体的工具使用步骤请参阅厂商文档。

## 第一章：对象命名规范

本章解决数仓内"由于命名混乱导致找不到数据或误用数据"的问题。

> **完整命名规则请查阅**：[《命名标准》](/Doc_Viewer.html?file=docs/standard/命名标准.md)
>
> 以下为管理要点摘要，详细的命名格式、业务域注册表、字段后缀对照表等内容已独立为标准文档。

### 1.1 表命名管理要点

- **标准格式**：`{层级}_{业务域}_{业务对象}_{更新周期}`
- 严禁出现无前缀的"孤儿表"
- 表名变更必须同步更新数据字典，确保"血缘"可追溯
- 业务域简称须从注册表中选取（详见[《命名标准》第一章「业务域注册表」](/Doc_Viewer.html?file=docs/standard/命名标准.md)）

### 1.2 字段命名管理要点

- 字段名应具备自解释性
- 后缀约束：金额 `_amt`、日期 `_dt`、标志 `_flg`、状态 `_sts`（详见[《命名标准》第二章「字段后缀标准」](/Doc_Viewer.html?file=docs/standard/命名标准.md)）
- 看到 `_amt` 必须核查数据类型；看到 `_sts` 必须核查对应的状态映射文档

## 第二章：数据架构与分层设计

本章解决"数据流转路径混乱、计算逻辑重复"的问题。

> **分层架构详细定义请查阅**：[《分层标准》](/Doc_Viewer.html?file=docs/standard/分层标准.md)
>
> **公共字段完整规格请查阅**：[《通用字段标准》](/Doc_Viewer.html?file=docs/standard/通用字段标准.md)
>
> 以下保留管理要点和操作指引，字段规格表、分层定义等查阅型内容已独立为标准文档。

### 2.1 分层流转原则

- **单向流转**：数据只能从低层流向高层（ODS → DWD → DWS → ADS）
- **禁止跨层**：严禁 ADS 层直接调用 ODS 层原始数据
- **高内聚低耦合**：业务逻辑应尽量在 DWD 层沉淀
- **铁律**：所有指标必须基于 DWD 事实表计算，严禁直连 ODS
- 不确定数据放哪层时，查阅[《分层标准》第四章「层级判定速查表」](/Doc_Viewer.html?file=docs/standard/分层标准.md)

### 2.2 公共审计字段

每张物理表**必须**包含对应层级的审计字段（完整字段定义见[《通用字段标准》第一章「审计字段」](/Doc_Viewer.html?file=docs/standard/通用字段标准.md)）。

**管理要点**：
- 审计字段是"数据质量溯源"的唯一抓手，缺失审计字段的视为"不可靠资产"，禁止上线
- 所有 `dw_` 字段必须 NOT NULL
- 严禁业务逻辑修改 `dw_` 开头的字段值

##### dw_batch_id 配置说明（FDL）

由于 ODS 同步采用全量策略（Truncate & Reload），同一批次的所有记录 `dw_batch_id` 必须保持一致。**禁止使用 `GETDATE()` 作为批次号**，因为每条记录写入时间不同会导致批次号不一致。

**推荐配置方式：** 在 FDL 数据同步节点后增加一个「SQL 脚本」节点，统一更新 `dw_batch_id`：

```sql
-- 在数据同步节点后执行，统一设置批次号
UPDATE ods_xxx_df
SET dw_batch_id =
    REPLACE(
        REPLACE(
            REPLACE('${cyctime}', '-', ''),
        ' ', ''),
    ':', '');
```

**参数说明：**
- `${cyctime}`：FDL 内置参数，表示任务调度时间（格式：`yyyy-MM-dd HH:mm:ss`）
- 经过三层 `REPLACE` 处理后，转换为 `yyyyMMddHHmmss` 格式（如：`20260109143000`）

**注意事项：**
1. SQL 脚本节点需选择与 ODS 表相同的数据库连接
2. 确保 `dw_batch_id` 字段允许为空或有默认值，避免同步阶段报错
3. 该步骤在数据同步**完成后**执行，不影响同步性能

## 第三章：开发与存储技术规范

本章解决“系统性能低下、计算结果不准”的问题。

### 3.1 字段类型选型

完整的数据类型对照表请查阅[《通用字段标准》第三章「数据类型选型」](/Doc_Viewer.html?file=docs/standard/通用字段标准.md)。

核心规则摘要：
- 金额必须使用 `DECIMAL(18,2)`，**严禁** FLOAT/DOUBLE
- 日期统一使用 `DATE` 或 `DATETIME`
- 布尔值统一 `TINYINT` (0/1) + `_flg` 后缀
- ID 类字段（身份证、超长编号）建议使用 `VARCHAR`
- ODS/DWD 字符串字段长度建议为源表的 1.5~2 倍

### 3.2 SQL 开发“红线”

#### 3.2.1 严禁 SELECT *

必须按需取数。

#### 3.2.2 注释要求

脚本头部必须有任务描述；复杂的 CASE WHEN 逻辑必须逐行注释。

**强制头部注释模板：**

```sql
/*
-- -----------------------------------------------------------------------------
-- 任务名      : dwd_cont_header_df
-- 目标表      : dwd_cont_header_df
-- 负责人      : 张三
-- 创建日期    : 2023-12-24
-- 任务描述    : 合同主表，从 ODS 清洗并关联字典翻译
-- 关联需求    : JIRA-DAT-1024
-- -----------------------------------------------------------------------------
-- 修改记录    :
-- 日期        版本    修改人    修改描述
-- 2023-12-24  v1.0    张三      初始开发
-- 2024-01-05  v1.1    李四      增加 discount_amt 字段 (JIRA-DAT-1099)
-- -----------------------------------------------------------------------------
*/
```

#### 3.2.3 空值处理 (NULL Handling)

对可能出现的 NULL 值必须进行 `COALESCE` 或 `ISNULL` 容错处理。
**默认填充标准：**

* **字符串**: 填 `'Unknown'` 或 `'-'`。
* **数值**: 填 `0` (金额/计数) 或 `-1` (ID类)。
* **日期**: 填 `'1900-01-01'`。
* **目的**: 确保报表端筛选 `!= 'A'` 时能包含这些空值记录。

#### 3.2.4 禁止存储过程 (No Stored Procedures)

**红线：** 严禁使用数据库存储过程（Stored Procedure）封装核心清洗逻辑。
**原因：** 存储过程是数据血缘解析的“黑盒”，会导致元数据管理系统无法自动抓取依赖关系。所有逻辑必须显性化为 `INSERT OVERWRITE ... SELECT ...` 的标准 SQL 任务。

#### 3.2.5 视图设计规范 (View Design)

* **层级限制**: 严禁视图嵌套深度超过 **3层**。
* **原因**: 过度嵌套的视图虽然逻辑看似隔离，但在出现数据偏差时极难排查，且会导致数仓性能呈指数级下降。建议优先将复杂逻辑沉淀为物理表 (DWD/DWS)。

#### 3.2.6 SQL 书写规范

* **关键字**: 统一大写 (`SELECT`, `FROM`, `WHERE`)。
* **对齐**: 字段名对齐，逗号置前或置后统一。
* **缩进**: 统一使用 4 空格缩进，增强代码可读性。

**管理要点：**评审时重点检查涉及资金计算的 SQL，确保分母非零及精度处理符合财务标准。

### 3.3 维度建模执行标准

#### 3.3.1 星型模型架构

强制区分事实表（Fact）与维度表（Dim）。DWD层须保留最细粒度的原子业务过程，禁止在底层进行不可逆的聚合。

#### 3.3.2 拉链表设计（SCD2）

针对组织架构、合同状态等变动频繁且需回溯的属性，强制采用拉链表存储。
**例外条款：** 对明确属于“数据纠错”且后续无需分析历史变更的非关键属性（如备注修正），允许采用覆盖更新 (SCD1) 方式。

### 3.4 FDL 采集层适配规范

* **任务粒度**: 一个 data pipe 任务原则上只处理一张表，禁止单任务内并行过多“数据流”，以保证 FDL 实例调度的容错性。
* **参数化配置**: 源库连接信息、目标库 Schema 必须使用 FDL 的“全局参数”或“系统参数”管理，禁止在 SQL 脚本中明文写死 IP 和密码。
* **脏数据处理**: FDL 任务必须开启“脏数据记录”功能，将不符合类型约束的数据清洗至 `err_` 表，严禁直接丢弃导致数据丢失。

### 3.5 数据安全与隐私保护

* **敏感数据处理**: 手机号、身份证号在 ODS 层保留明文（受限访问）。
* **脱敏 / 加密**: 进入 DWD/DWS 层必须进行掩码处理（如 `138****0000`）或加密存储。
* **权限隔离**: 薪资 (`_amt`) 等高敏感字段建议单独拆表或通过视图控制访问权限。

### 3.6 数据同步与集成策略

* **全量 vs 增量 (ODS策略)**:
  * **优先全量 (Daily Snapshot)**: 在数据量可控的前提下（如单表行数处于可接受范围，建议参考值 < 5000万），ODS 层优先采用“每日全量快照”方式（Truncate & Reload）。这是用存储空间换取数据一致性的最佳实践。
  * **大表增量**: 仅针对超大数据量流水表，采用基于 `update_time` 的增量合并策略。
* **硬删除处理**:
  * 若采用 **全量重跑**，ODS 每次都是源系统最新快照，物理删除会自动同步（记录消失），需在 DWD 层通过快照对比识别“删除”状态。
  * 若采用 **增量同步**，源库物理删除的数据，ODS 层原则上保留最后快照，仅更新 `dw_is_active_flg`（注：本期项目暂不使用 CDC 技术，针对增量表的物理删除，需通过周期性“全量主键比对”或“T+7全量重跑”进行识别与标记）。
* **类型映射**: JSON/非结构化数据入仓时，须在 ODS/DWD 层解析为独立的结构化字段（推荐使用 `OPENJSON` 或 FDL 解析算子）。
* **源端批量订正 (Source Correction)**:
  * **场景**: 源系统对历史数据进行批量修复（如 Update 了半年前的 20 万行状态）。
  * **应对**:
    * **全量表**: 自动同步，无需特殊处理。
    * **增量表**: 涉及历史分区变更时，**必须通知**数仓团队手动级联重跑，否则无法保障一致性。

### 3.7 数据字典与指标规范

**原则：** 所有指标应明确依赖的 DWD 事实表，指标口径**不得绕过 DWD** 直接基于 ODS 或源系统数据计算。这是防止“野指标”的核心红线。

* **字典标准**: 必须注明业务归属域、数据负责人。枚举值字段（如 `status`）必须附带 `<值, 含义>` 对照表。
* **指标字典**: 明确区分 **原子指标**（如支付金额）与 **派生指标**（如近7天支付金额）。严禁同名不同义。

#### 3.7.1 指标命名标准化公式

为实现指标命名的"见名知意"，所有正式上线的指标英文名称必须严格遵循以下**五段式结构**：

> **公式：** `[前缀]_[业务对象]_[动作/修饰]_[度量/原子]_[时间周期]`

**1. 字段含义分解：**

* **前缀 (可选)**: 仅在特殊场景使用，如 `derived_` (派生)。
* **业务对象 (Object)**: 指标所属的实体，如 `cust` (客户), `ord` (订单), `emp` (员工)。
* **动作/修饰 (Action)**: 具体的业务过程或状态，如 `pay` (支付), `cancel` (取消), `active` (活跃)。
* **度量/原子 (Measure)**: 具体的计算口径缩写，如 `amt` (金额), `cnt` (次数/人数), `rate` (比率)。
* **时间周期 (Time)**: 统计窗口，如 `1d` (近1天), `7d` (近7天), `mtd` (月累计), `ytd` (年累计)。

**2. 规范示例与映射：**

| 指标中文名 | 命名解析 (对象+动作+度量+周期) | 标准英文名称 |
| :--- | :--- | :--- |
| **过去7天签约金额** | `cont` (合同) + `sign` (签约) + `amt` (金额) + `7d` | `cont_sign_amt_7d` |
| **员工入职总数** | `emp` (员工) + `enter` (入职) + `cnt` (数量) | `emp_enter_cnt` |
| **客户活跃标志** | `cust` (客户) + `active` (活跃) + `flg` (标志) | `cust_active_flg` |
| **财务月度报表** | `fin` (财务) + `monthly` (月度) + `report` (报表) | `ads_fin_monthly_report` |

**3. 命名红线与约束：**

* **后缀一致性**: 严格遵循手册定义，金额=`_amt`，数量=`_cnt`，标志=`_flg`，比率=`_rate`。
* **严禁同名不同义**: 新指标注册前**必须**检索字典。若口径不同，严禁使用已有名称。
* **版本标识**: 若发生重大口径变更，严禁覆盖历史逻辑，必须增加后缀（如 `_v2`）。
* **废弃标记**: 不再维护的指标，须在元数据中标记 `[DEPRECATED]` 并设定下线缓冲期。

#### 3.7.2 指标注册与管理流程

每一个指标在上线前，必须在指标管理系统（或 Excel 字典）中完成“注册”，并具备以下身份信息：

| 属性 | 说明 | 示例 |
| --- | --- | --- |
| **指标名称** | 遵循上述五段式命名公式 | `new_user_pay_amt_7d` |
| **业务口径** | 业务人员能看懂的自然语言定义 | 注册时间在7天内，且完成支付的订单总金额。 |
| **技术口径** | 具体的 SQL 逻辑公式 | `SUM(pay_amt) WHERE ...` |
| **业务负责人** | **谁定义的谁负责**。没有明确负责人的指标，拒绝开发。 | 财务部-王总监 |
| **技术负责人** | 负责保障计算准确性和产出及时性。 | 数仓组-张三 |

#### 3.7.3 指标版本与变更管理

**原则：** 指标口径变更必须考虑“历史数据的解释权”。

1. **Bug 修复 (Correction)**:
    * 定义：原口径实现有误（如写错了过滤条件）。
    * 操作：修正 SQL 逻辑，并**必须回刷**所有历史分区的数据，确保数据的一致性。
2. **业务规则变更 (Business Logic Change)**:
    * **小变更**（如调整某个分类的归属）：在指标字典中更新口径版本说明，代码中使用 `CASE WHEN dt >= '变更日期' THEN 新逻辑 ELSE 旧逻辑 END` 进行切割，保留历史数据的真实样貌。
    * **大变更**（如改变了计算公式的分子分母）：
        * **严禁**直接修改原指标逻辑覆盖历史。
        * **必须**新建指标（命名可带后缀，如 `_v2` 或更能体现业务含义的后缀 `_ex_tax`），并将原指标标记为 `[DEPRECATED]`（已废弃）。
3. **废弃下线**:
    * 废弃的指标/报表，必须邮件通知所有下游用户，在元数据中心标记“预计下线日期”，保留 30 天缓冲期后停止计算。

### 3.8 开发避坑指南

* **禁止硬编码**: SQL 中严禁出现 `WHERE id = 1001` 等魔法数字，必须关联维度表或使用参数。
* **时区处理**: 所有时间字段统一转换为服务器时区（如 UTC+8），禁止混用。
* **配置化管理**: 重复使用的阈值、常量应抽取至 DIM 层的配置表中。

### 3.9 常见开发痛点与解决方案

* **运维期间的阻塞 (Locking during Maintenance)**
  * **场景**: 虽然数仓采用 T+1 错峰调度，但在 **白天紧急修复历史数据** 或 **临时跑批** 时，可能会与业务查询产生锁竞争。
  * **建议**: 仅在白天进行人工运维操作且需从生产表取数时，建议加上 `WITH(NOLOCK)` 以避免阻塞正在写入的修复任务。常规夜间 T+1 调度任务无需强制添加。
* **关联键倾斜 (Data Skew)**
  * **痛点**: 某张大表 Join 时进度停滞，源于 NULL 值过多聚集。
  * **规范**: 在关联（`ON a.id = b.id`）前，必须在 WHERE 子句中剔除 `a.id IS NULL` 的数据。
* **字段截断 (Truncation)**
  * **痛点**: 源系统字段扩容，导致数仓 ETL 报错 stopping。
  * **规范**: ODS/DWD 建表时，String 类型字段长度建议设为源表的 **1.5倍 至 2倍**，预留变更空间。
* **大事务膨胀 (Log Full)**
  * **痛点**: 单次操作过大数据量（如 >1000万行）导致数据库日志爆满回滚缓慢。
  * **规范**: 严禁一次性 Delete/Update 全表，必须采用分批处理（Batch Processing），每批建议 10-50 万行。

## 第四章：数据质量与验收规范

本章解决“数据不可信、不敢用”的问题。

### 4.1 核心对账流程 (Automated Validation)

开发人员在任务上线前，必须在 ETL 脚本末尾或 FDL 质量算子中嵌入以下**标准化对账 SQL**。

#### 4.1.1 总量对账 (Row Count Check)

验证源表与目标表记录数是否一致，识别抽取过程中的漏数问题。

```sql
SELECT 
    'Row_Count_Check' AS check_type,
    (SELECT COUNT(1) FROM ods_contracts WHERE dw_batch_id = '${fdl_instance_id}') AS source_cnt, 
    (SELECT COUNT(1) FROM dwd_contracts WHERE dw_batch_id = '${fdl_instance_id}') AS target_cnt,
    CASE 
        WHEN (SELECT COUNT(1) FROM ods_contracts) = (SELECT COUNT(1) FROM dwd_contracts) THEN 'PASS' 
        ELSE 'FAIL' 
    END AS status;
```

#### 4.1.2 关键指标对账 (Value Sum Check)

验证核心金额字段在清洗加工后，总额是否发生非预期偏移。

```sql
SELECT 
    'Amount_Sum_Check' AS check_type,
    SUM(src_amt) AS source_amt,         -- ODS层原始金额
    SUM(target_amt) AS target_amt,      -- DWD层加工后金额
    ABS(SUM(src_amt) - SUM(target_amt)) AS diff -- 差异绝对值
FROM validation_view_temp;              -- 建议通过 CTE 或临时视图关联比对
```

#### 4.1.3 主键唯一性对账 (Duplicate Check)

检查目标表是否存在由于关联逻辑（Join）导致的“数据膨胀”或重复行。**若返回结果大于0，必须阻断任务。**

```sql
SELECT 
    primary_key, 
    COUNT(1) AS dup_cnt
FROM dwd_table_name
WHERE dw_batch_id = '${fdl_instance_id}' -- 仅检查当前运行批次
GROUP BY primary_key
HAVING COUNT(1) > 1;
```

**对账红线：**

1. **强制约束**：所有参与对账的字段（如 `dw_batch_id`）必须为 `NOT NULL`。
2. **异常中断**：以上任意检查项返回 `FAIL` 或 `dup_cnt > 0`，ETL 任务**必须抛出异常退出**，严禁静默完成从而污染下游报表。

### 4.2 任务监控规范

#### 4.2.1 FineDataLink (FDL) 配置

必须配置失败重试（建议 3 次）。

#### 4.2.2 必须关联至业务负责人的告警通道

**管理要点：**“对账不平”或“无监控配置”的任务，不允许加入生产调度。

### 4.3 数据回刷（Backfill）机制

* **幂等重跑**: 当业务逻辑变更或源头数据修复时，利用 `dw_batch_id` 进行幂等重跑。
* **相关审批**: 必须规定回刷数据的审批流程，评估对下游报表的影响。

### 4.4 数据生命周期 (TTL)

* **历史归档**: ODS层历史数据建议保留 30 天后归档至冷存储或删除。
* **临时清理**: 系统应配置策略自动清理超过 7 天的 `tmp_` 表。

## 第五章：管理流程与职责划分 (SOP)

本章解决“重构过程失控、责任推诿”的问题。核心原则：**业务不签字，不敢写代码。**

### 5.1 DWD 层设计与验收流程

#### 5.1.1 需求与逻辑设计 (Mapping)

1. **立项**: 业务方提出分析需求或指标需求。
2. **逻辑映射 (Mapping Doc)**: 开发人员必须输出 Excel 格式的《DWD逻辑映射文档》。
   * **字段级血缘**: 必须在文档中标注每个字段的 **变换逻辑 (Transformation)**，如“直接映射”、“枚举转换”或“逻辑聚合/公式计算”，以便后续自动化治理。

#### 5.1.2 DWD 模型构建模式 (Modeling Patterns)

**原则：** DWD 表在上线前，应确保核心业务人员能够理解该表所表达的业务事实，包括每行记录的业务含义、关键字段的业务意义以及数据变化的原因。

1. **1:1 清洗 (规范化)**: 源表完整涵盖单一业务过程（如合同/标书主表）。仅做脏数据清洗、枚举值统一。
2. **N:1 宽表化 (关联/Join)**: 业务过程分散在多张表（如 合同=主表+明细表+结算单）。
   * **禁止条款**: DWD 层**严禁**进行不可拆解的聚合操作（Sum/Count），必须保持明细粒度。

#### 5.1.3 UAT 验收标准（结果导向）

验收的核心标准不再是“看懂文档”，而是**“对齐结果”**。

1. **技术自证 (Mandatory)**:
   * 开发人员必须提供**《数据抽样比对报告》**，需包含至少 5-10 个典型业务样本在 源系统界面 VS 数仓表查询结果 的**同屏对比截图**。
   * **覆盖率要求**: 样本必须覆盖 **“标准合同/结算单”、“变更/红冲单”、“历史跨期/特殊单”** 三类典型场景，确保逻辑在极端情况下依然稳健。
   * **原则**: “有图有真相”。哪怕 Mapping 写得再完美，只要截图对不上，视为开发失败。
2. **业务复核 (Spot Check)**:
   * 业务人员只需审阅上述截图证据。
   * 若结果一致，回复“确认”邮件即视为验收通过。
   * 若业务方放弃复核，上线后出现的数据异议，以技术部门提供的截图逻辑为准。

#### 5.1.4 上线观察期 (Observation Period)

建议对涉及资金或核心指标的任务增加 **3-5天** 的“静默观察期”。

* **标识**: 观察期内输出的报表/看板须标注 `[测试中]` 或 `[Beta]` 字样。
* **转正**: 经过至少一周的数据产出与源系统对比无误后，由业务方邮件确认“转正”，方可移除测试标识。

### 5.2 职责划分 SOP

* **需求评审**: 明确口径（邮件确认）。
* **模型审核**: 物理建表前，审核表名、字段名及类型。
* **验收闭环**: 提交《数据抽样比对报告》并获得业务确认。
* **发布上线**: 正式部署至生产环境 FDL。

## 附录A：执行说明

本章所定义的管理流程与职责划分，是数仓重构及后续数据建设工作的统一执行规范。凡纳入公司数仓体系的正式数据资产，均须严格遵循上述流程实施。任何未按流程完成评审、审核或对账验收的数据对象，不得进入生产调度环境。

## 附录B：规则修订与版本管理说明

本文档作为数仓治理与执行的基准版本，在实际运行过程中可根据业务与技术环境变化进行迭代完善。
