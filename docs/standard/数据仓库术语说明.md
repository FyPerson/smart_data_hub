# 数据仓库与指标体系术语说明

> 本文档定义数据仓库建设及指标管理相关的核心术语，帮助团队成员统一理解数仓概念、技术规范和指标体系。

---

## 技术平台说明

本项目数据仓库建设采用以下技术平台：

| 组件 | 技术选型 | 说明 |
|------|----------|------|
| **数据仓库** | Microsoft SQL Server | 目标数仓数据库，存储 ODS/DIM/DWD/DWS/ADS 各层数据 |
| **数据同步** | FineDataLink (FDL) | 帆软数据集成平台，负责数据抽取、转换、加载 |
| **任务调度** | FDL 内置调度 | 支持 Cron 表达式配置，任务依赖管理 |
| **开发管理** | 智数协同平台 | 本平台，负责模型注册、脚本生成、任务跟踪 |

**数据流向**：
```
源系统(BMS/CRM等) → FDL同步 → SQL Server ODS层 → ETL处理 → DIM/DWD/DWS/ADS
```

## 概述：什么是数据仓库

### 定义

**数据仓库（Data Warehouse，简称 DW）** 是一个面向分析的、集成的、相对稳定的、反映历史变化的数据集合，用于支持企业决策分析。

简单来说，数据仓库就是把散落在各个业务系统中的数据**汇总、清洗、整合**到一起，形成一个专门用于**查询和分析**的数据库。

### 数仓 vs 业务数据库

| 对比项 | 业务数据库 (OLTP) | 数据仓库 (OLAP) |
|--------|-------------------|-----------------|
| **设计目标** | 支撑日常业务操作 | 支撑数据分析和决策 |
| **数据范围** | 单个业务系统 | 跨多个业务系统整合 |
| **操作类型** | 频繁增删改查 | 主要是查询，很少修改 |
| **数据时效** | 当前状态 | 历史累积 |
| **查询特点** | 简单查询，返回少量记录 | 复杂聚合，扫描大量数据 |
| **典型用户** | 业务人员（录入订单、处理工单） | 分析师、管理层（看报表、做决策） |

**举例说明**：
- **业务数据库**：销售人员在 CRM 系统录入一条客户信息，系统立即保存
- **数据仓库**：分析师查询"过去 3 年各区域客户增长趋势"，需要整合 CRM、订单、财务等多个系统的数据

### 为什么需要数据仓库

| 痛点 | 没有数仓时 | 有数仓后 |
|------|-----------|---------|
| **数据分散** | 客户在 CRM、订单在 ERP、财务在用友，想看完整客户画像要跑三个系统 | 数据统一汇聚，一张表看全貌 |
| **口径不一** | 销售说本月成交 500 万，财务说只有 480 万，吵了一下午 | 统一指标定义，数出同源 |
| **影响生产** | 跑个复杂报表把业务库拖慢了，被业务投诉 | 分析查询在数仓执行，不影响生产系统 |
| **历史丢失** | 客户上个月还是 VIP，这个月降级了，但查不到历史记录 | SCD2 保留完整变更历史 |
| **重复开发** | 每个报表都要重新写 SQL 关联十几张表 | 建好模型后，报表开发效率大幅提升 |

### 数仓的核心能力

| 能力 | 说明 |
|------|------|
| **数据集成** | 从多个源系统抽取数据，统一存储 |
| **数据清洗** | 处理脏数据、空值、重复、格式不一致 |
| **数据建模** | 按业务主题组织数据，便于分析 |
| **指标计算** | 定义统一口径，计算业务指标 |
| **历史追溯** | 保留数据变化历史，支持时间穿越分析 |
| **高效查询** | 针对分析场景优化，支持大数据量聚合查询 |

## 一、数仓架构

### 1.1 数据分层

#### ODS 层 (Operational Data Store)

**定义**：操作数据存储层，也称贴源层，是数据仓库的最底层。

**特点**：
- 与源系统表结构一一对应，保持原始数据格式
- 不做业务逻辑处理，仅做字段类型适配
- 保留全部历史数据或增量数据
- 作为后续分层的数据来源

**命名规范**：`ods_{表名}_df`

> **说明**：当前数据源均来自单一业务系统（BMS），ODS 表名不再包含源系统前缀。若后续接入多个独立源系统，可在表名中增加系统标识以区分。

**示例**：
| ODS 表名 | 源表 | 说明 |
|----------|------|------|
| ods_contract_df | BMS.dbo.Contract | 合同主表 |
| ods_base_data_item_df | BMS.dbo.BaseDataItem | 基础字典表 |

---

#### DIM 层 (Dimension)

**定义**：维度层，存储维度数据，为分析提供描述性信息。

**特点**：
- 存储维度主数据（客户、产品、组织等）
- 支持 SCD（缓慢变化维）处理
- 提供代理键（Surrogate Key）关联事实表
- 数据相对稳定，变化频率低

**命名规范**：`dim_{业务对象}`

**示例**：
| DIM 表名 | 说明 | SCD 类型 |
|----------|------|----------|
| dim_customer | 客户维度表 | SCD2 |
| dim_product | 产品维度表 | SCD1 |
| dim_organization | 组织架构维度表 | SCD2 |
| dim_date | 日期维度表 | 静态 |

---

#### DWD 层 (Data Warehouse Detail)

**定义**：明细数据层，存储经过清洗、标准化的业务明细数据。

**特点**：
- 以业务过程为建模驱动
- 保持最细粒度，不做聚合
- 完成数据清洗、去重、标准化
- 关联维度表，形成宽表

**命名规范**：`dwd_{业务域}_{业务对象}_{更新周期}`

> **说明**：业务域使用公司注册的简称（见下方业务域注册表），业务对象不应与业务域名称重复。更新周期常用 `_df`（日全量）和 `_di`（日增量）。

**已注册业务域简称**：

| 简称 | 业务域 | 英文全称 |
|------|--------|----------|
| cont | 合同 | Contract |
| bid | 招投标 | Bidding |
| pub | 公共 | Public |
| fin | 财务 | Finance |
| proj | 项目 | Project |
| dlvr | 交付 | Delivery |

**示例**：
| DWD 表名 | 说明 | 粒度 |
|----------|------|------|
| dwd_cont_header_df | 合同主表 | 合同 |
| dwd_cont_renew_chain_df | 合同续签链路表 | 合同 |
| dwd_fin_payment_df | 回款/付款明细 | 支付单 |

---

#### DWS 层 (Data Warehouse Summary)

**定义**：汇总数据层，存储按主题域汇总的数据。

**特点**：
- 按不同粒度聚合 DWD 层数据
- 以分析主题为建模驱动
- 提供常用的汇总指标
- 支持上卷下钻分析

**命名规范**：`dws_{主题}_{粒度}_{周期}`

**示例**：
| DWS 表名 | 说明 | 粒度 |
|----------|------|------|
| dws_trade_store_1d | 门店交易日汇总 | 门店 + 日 |
| dws_user_action_1d | 用户行为日汇总 | 用户 + 日 |
| dws_product_sale_1m | 商品销售月汇总 | 商品 + 月 |

---

#### ADS 层 (Application Data Store)

**定义**：应用数据层，面向特定应用场景的数据集市。

**特点**：
- 直接服务于报表、BI、数据产品
- 高度定制化，满足特定业务需求
- 可能包含跨主题的数据
- 查询性能优先

**命名规范**：`ads_{应用场景}_{内容描述}`

**示例**：
| ADS 表名 | 说明 | 使用场景 |
|----------|------|----------|
| ads_dashboard_kpi | 经营看板 KPI | 管理驾驶舱 |
| ads_report_monthly_sales | 月度销售报表 | 财务报表 |
| ads_api_user_profile | 用户画像接口表 | 推荐系统 |

---

### 1.2 数据流向

```
源系统 → ODS → DWD → DWS → ADS → 应用
           ↓
          DIM (维度表供各层使用)
```

**数据流说明**：
- **抽取 (Extract)**：从源系统抽取数据到 ODS
- **清洗 (Clean)**：ODS 到 DWD 的数据清洗和标准化
- **整合 (Integrate)**：DWD 关联维度形成宽表
- **汇总 (Aggregate)**：DWD 到 DWS 的聚合计算
- **应用 (Serve)**：DWS 到 ADS 面向应用输出

## 二、维度建模

### 2.1 事实表 (Fact Table)

**定义**：存储业务过程度量值的表，是维度模型的核心。

**类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **事务事实表** | 记录业务事件，粒度为单次事务 | 订单事实表、支付事实表 |
| **周期快照事实表** | 定期记录状态快照 | 库存日快照、账户余额月快照 |
| **累积快照事实表** | 记录业务过程多个里程碑 | 订单生命周期表（下单→支付→发货→签收） |
| **无事实事实表** | 只记录事件发生，无度量值 | 用户登录日志、页面访问记录 |

---

### 2.2 维度表 (Dimension Table)

**定义**：描述业务实体属性的表，为事实表提供分析上下文。

**常见维度类型**：

| 维度类型 | 说明 | 示例 |
|----------|------|------|
| **普通维度** | 标准的维度表 | 产品维度、客户维度 |
| **日期维度** | 时间相关属性 | 日期、周、月、季度、年、节假日标识 |
| **退化维度** | 存储在事实表中的维度 | 订单号、发票号 |
| **杂项维度** | 低基数属性的集合 | 订单状态组合、支付方式组合 |
| **角色扮演维度** | 同一维度表多次关联 | 下单日期、发货日期都关联日期维度 |

---

### 2.3 缓慢变化维 (SCD - Slowly Changing Dimension)

**定义**：处理维度属性随时间变化的技术方案。

**什么是缓慢变化维？**

SCD 全称 Slowly Changing Dimension（缓慢变化维度），是维度建模中处理维度数据变化的标准方法。与事实数据（如订单、交易）的高频产生不同，维度数据（如客户信息、产品属性）变化相对缓慢——可能几周、几个月甚至几年才发生一次变更。

**为什么需要 SCD？**

在业务运营过程中，维度属性不可避免地会发生变化：
- 客户搬家，地址发生变更
- 员工升职，职级从"专员"变为"经理"
- 产品调价，单价从 99 元变为 129 元
- 门店更名，名称从"朝阳店"变为"CBD 旗舰店"

当这些变化发生时，数仓需要决定：**是否保留历史状态？如何保留？** 这就是 SCD 要解决的核心问题。

**业务场景举例**

| 变化场景 | 业务问题 | SCD 选择 |
|----------|----------|----------|
| 客户手机号变更 | 只需要最新联系方式 | **Type 1** - 直接覆盖 |
| 客户等级从普通升级为 VIP | 需要分析升级前后消费行为差异 | **Type 2** - 保留历史 |
| 销售归属区域调整 | 只关心调整前后两个状态 | **Type 3** - 保留前值 |
| 员工所属部门变动 | 按历史部门统计人效时需要追溯 | **Type 2** - 保留历史 |
| 商品更正错误的分类标签 | 历史数据也应该用正确的分类 | **Type 1** - 直接覆盖 |

**SCD 类型速览**

| 类型 | 策略 | 保留历史 | 存储成本 | 查询复杂度 |
|------|------|----------|----------|------------|
| Type 1 | 覆盖更新 | ❌ 不保留 | 低 | 简单 |
| Type 2 | 新增版本 | ✅ 完整保留 | 高 | 较复杂 |
| Type 3 | 保留前值 | ⚠️ 仅一次 | 中 | 中等 |

---

#### SCD Type 1 (覆盖更新)

**策略**：直接用新值覆盖旧值，不保留历史。

**特点**：
- 实现简单，存储成本低
- 无法追溯历史状态
- 适用于错误修正或不关心历史的场景

**示例**：
```sql
-- 更新客户电话号码，直接覆盖
UPDATE dim_customer SET phone = '13800138001' WHERE customer_id = 100;
```

---

#### SCD Type 2 (历史追踪)

**策略**：新增记录保留历史版本，通过有效期标识当前版本。

**特点**：
- 完整保留历史变化
- 需要额外的版本控制字段
- 存储成本较高
- 适用于需要分析历史状态的场景

**必要字段**：
| 字段 | 说明 |
|------|------|
| sk_xxx | 代理键（自增主键） |
| valid_from | 版本生效日期 |
| valid_to | 版本失效日期 |
| is_current | 是否当前版本 (1/0) |

**示例**：
| sk | customer_id | name | level | valid_from | valid_to | is_current |
|----|-------------|------|-------|------------|----------|------------|
| 1 | C001 | 张三 | 普通 | 2024-01-01 | 2024-06-30 | 0 |
| 2 | C001 | 张三 | VIP | 2024-07-01 | 9999-12-31 | 1 |

---

#### SCD Type 3 (有限历史)

**策略**：增加列存储前一个值，只保留最近一次变化。

**特点**：
- 只能追溯一次变化
- 实现相对简单
- 适用于只关心当前值和上一个值的场景

**示例**：
| customer_id | current_level | previous_level | level_change_date |
|-------------|---------------|----------------|-------------------|
| C001 | VIP | 普通 | 2024-07-01 |

---

### 2.4 星型模型 (Star Schema)

**定义**：以事实表为中心，维度表直接连接事实表的结构。

**特点**：
- 结构简单，易于理解
- 查询性能好，JOIN 层级少
- 可能存在数据冗余
- 是最常用的数仓模型

```
        dim_date
            │
dim_customer ─┼─ fact_order ─── dim_product
            │
        dim_store
```

---

### 2.5 雪花模型 (Snowflake Schema)

**定义**：维度表进一步规范化，形成多级层次结构。

**特点**：
- 减少数据冗余
- 结构更规范化
- 查询时需要更多 JOIN
- 维护复杂度较高

```
dim_region ─── dim_store ─┬─ fact_order ─── dim_product ─── dim_category
                          │
              dim_customer
```

---

### 2.6 代理键 (Surrogate Key)

**定义**：数仓内部生成的无业务含义的唯一标识，通常为自增整数。

**作用**：
- 隔离业务系统主键变化的影响
- 支持 SCD2 多版本记录
- 提高 JOIN 性能（整数比字符串快）
- 处理多源系统主键冲突

**命名规范**：`sk_{业务对象}` 或 `{表名}_sk`

**示例**：
| 字段 | 类型 | 说明 |
|------|------|------|
| sk_customer | BIGINT IDENTITY | 代理键（自增） |
| customer_id | VARCHAR(50) | 业务键（来自源系统） |

> **平台配置提示**：在智数协同平台中配置 DIM 模型时，代理键会根据业务标识字段自动命名和生成，无需手动配置。

---

### 2.7 业务键 (Business Key / Natural Key)

**定义**：来自源系统的业务主键，具有实际业务含义。

**特点**：
- 由业务系统定义和维护
- 可能随业务规则变化
- 用于追溯源系统数据
- 在 SCD2 中用于识别同一业务实体

**示例**：客户编号、合同编号、产品 SKU

> **术语说明**：在智数协同平台的配置界面中，业务键显示为"业务标识"，以避免与物理主键（PRIMARY KEY）混淆。对于 SCD2 维度表，物理主键是自动生成的代理键，业务键用于识别同一业务实体的不同版本。

## 三、ETL 相关

### 3.1 ETL (Extract-Transform-Load)

**定义**：数据仓库数据集成的核心流程。

| 阶段 | 说明 | 典型操作 |
|------|------|----------|
| **Extract** | 从源系统抽取数据 | 全量抽取、增量抽取、CDC |
| **Transform** | 数据清洗和转换 | 类型转换、去重、标准化、关联 |
| **Load** | 加载到目标表 | INSERT、MERGE、分区加载 |

---

### 3.2 ELT (Extract-Load-Transform)

**定义**：先加载原始数据到数仓，再在数仓内部完成转换。

**特点**：
- 利用数仓的计算能力
- 保留原始数据，转换逻辑可追溯
- 适合大数据量场景
- 现代云数仓的主流模式

---

### 3.3 全量加载 (Full Load)

**定义**：每次同步全部数据，覆盖或替换目标表。

**适用场景**：
- 数据量较小（< 100万行）
- 源表无法提供增量标识
- 维度表初始化
- 数据修复/重跑

**实现方式**：
```sql
TRUNCATE TABLE target_table;
INSERT INTO target_table SELECT * FROM source_table;
```

---

### 3.4 增量加载 (Incremental Load)

**定义**：只同步自上次加载以来新增或变化的数据。

**增量识别方式**：

| 方式 | 说明 | 适用场景 |
|------|------|----------|
| **时间戳** | 根据更新时间筛选 | 有 update_time 字段的表 |
| **自增 ID** | 根据主键范围筛选 | 只新增不更新的表 |
| **CDC** | 捕获数据变更日志 | 需要捕获所有变更类型 |
| **全量比对** | 新旧数据对比差异 | 无增量标识的小表 |

---

### 3.5 CDC (Change Data Capture)

**定义**：变更数据捕获，识别源系统数据的增删改操作。

**实现方式**：

| 方式 | 说明 | 特点 |
|------|------|------|
| **日志解析** | 解析数据库事务日志 | 实时性高，对源库无侵入 |
| **触发器** | 通过触发器记录变更 | 实现简单，但影响源库性能 |
| **时间戳比对** | 比较最后更新时间 | 无法捕获删除操作 |
| **快照比对** | 新旧快照对比差异 | 可以捕获所有变更，但计算量大 |

**主流数据库 CDC 支持**：

| 数据库 | CDC 功能 | 启用方式 | 说明 |
|--------|----------|----------|------|
| **SQL Server** | 原生 CDC | `sys.sp_cdc_enable_table` | 需要 SQL Server Agent 服务运行 |
| **MySQL** | Binlog | `log_bin=ON, binlog_format=ROW` | 需配置 my.cnf 并重启 |
| **PostgreSQL** | 逻辑复制 | `wal_level=logical` | 需配置 pg_hba.conf 允许复制连接 |
| **Oracle** | LogMiner / GoldenGate | 需 DBA 配置 | 企业版功能，需额外授权 |

**SQL Server CDC 启用示例**：

```sql
-- 1. 数据库级别启用 CDC
EXEC sys.sp_cdc_enable_db;

-- 2. 表级别启用 CDC（需指定角色）
EXEC sys.sp_cdc_enable_table
    @source_schema = N'dbo',
    @source_name = N'Customer',
    @role_name = NULL,           -- NULL 表示不限制访问
    @supports_net_changes = 1;   -- 支持净变更查询

-- 3. 查询变更数据
SELECT * FROM cdc.dbo_Customer_CT
WHERE __$operation IN (1, 2, 4); -- 1=删除, 2=插入, 4=更新后
```

**注意事项**：
- CDC 功能需要数据库管理员配合开启，开发人员通常没有权限
- 日志解析方式对磁盘空间有要求，需定期清理历史变更记录
- 生产环境启用前需评估对源库性能的影响
- 建议在测试环境充分验证后再上线

---

### 3.6 数据清洗 (Data Cleansing)

**定义**：修正或删除数据中的错误、不一致和缺失值。

**常见清洗操作**：

| 操作 | 说明 | 示例 |
|------|------|------|
| **去重** | 删除重复记录 | 根据业务键去重 |
| **空值处理** | 填充或标记空值 | COALESCE(field, '未知') |
| **格式标准化** | 统一数据格式 | 日期格式、编码格式 |
| **异常值处理** | 识别和处理离群值 | 负数金额、未来日期 |
| **数据类型转换** | 适配目标表类型 | VARCHAR → DATE |

---

### 3.7 数据转换 (Data Transformation)

**定义**：将源数据转换为满足业务和技术要求的目标格式。

**常见转换类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **映射转换** | 值的对应转换 | 状态码 → 状态名称 |
| **派生计算** | 基于现有字段计算新字段 | 单价 × 数量 = 金额 |
| **聚合计算** | 汇总统计 | SUM、COUNT、AVG |
| **拆分合并** | 字段的拆分或合并 | 全名 → 姓 + 名 |
| **行列转换** | PIVOT/UNPIVOT | 月份列 → 月份行 |

---

### 3.8 MERGE 操作

**定义**：根据匹配条件决定插入、更新或删除的合并操作。

**语法结构**：
```sql
MERGE INTO target_table AS t
USING source_table AS s
ON t.business_key = s.business_key
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...
WHEN NOT MATCHED BY SOURCE THEN DELETE;
```

**应用场景**：
- SCD Type 1 更新
- 增量数据合并
- 数据同步

---

## 四、数据质量

### 4.1 数据质量维度

| 维度 | 说明 | 检查示例 |
|------|------|----------|
| **完整性** | 数据是否完整，无缺失 | 必填字段空值率 < 1% |
| **准确性** | 数据是否正确反映真实情况 | 金额与源系统一致 |
| **一致性** | 不同系统间数据是否一致 | 订单数与支付数匹配 |
| **及时性** | 数据是否按时更新 | T+1 数据在次日 8:00 前就绪 |
| **唯一性** | 是否存在重复数据 | 主键无重复 |
| **有效性** | 数据是否符合业务规则 | 日期在合理范围内 |

---

### 4.2 数据质量检查

**常见检查项**：

| 检查类型 | 说明 | SQL 示例 |
|----------|------|----------|
| **行数检查** | 验证数据量是否正常 | `SELECT COUNT(*) FROM table` |
| **主键唯一** | 检查主键是否重复 | `GROUP BY pk HAVING COUNT(*) > 1` |
| **空值检查** | 检查必填字段空值 | `WHERE column IS NULL` |
| **范围检查** | 验证值在合理范围 | `WHERE amount < 0` |
| **参照完整性** | 检查外键关联 | `LEFT JOIN ... WHERE fk IS NULL` |
| **跨表一致性** | 不同表数据对比 | 事实表数量 = 维度关联后数量 |

---

### 4.3 数据血缘 (Data Lineage)

**定义**：描述数据从源到目标的流转路径和转换过程。

**血缘类型**：

| 类型 | 说明 |
|------|------|
| **表级血缘** | 表与表之间的依赖关系 |
| **字段级血缘** | 字段与字段之间的映射关系 |
| **任务级血缘** | ETL 任务之间的依赖关系 |

**血缘用途**：
- 影响分析：源表变更影响哪些下游
- 根因分析：数据问题追溯到源头
- 合规审计：数据使用和流转记录

---

### 4.4 数据资产 (Data Asset)

**定义**：经过治理、具有业务价值的数据集合。

**资产要素**：
- **元数据**：表结构、字段说明、负责人
- **质量信息**：数据质量评分、检查结果
- **使用信息**：访问频次、使用场景
- **血缘信息**：上下游依赖关系

---

## 五、调度与运维

### 5.1 数据调度 (Data Scheduling)

**定义**：按照预定时间和依赖关系自动执行 ETL 任务。

**调度要素**：

| 要素 | 说明 |
|------|------|
| **调度周期** | 执行频率（日调度、小时调度） |
| **调度时间** | 具体执行时间点 |
| **依赖关系** | 上游任务完成后才能执行 |
| **重试策略** | 失败后的重试次数和间隔 |
| **超时设置** | 任务最长执行时间 |

---

### 5.2 批处理 (Batch Processing)

**定义**：按固定周期批量处理数据的模式。

**特点**：
- 通常 T+1 处理（隔天处理前一天数据）
- 数据有一定延迟
- 吞吐量大，成本较低
- 适合报表、分析等场景

---

### 5.3 实时处理 (Real-time Processing)

**定义**：数据产生后立即处理的模式。

**特点**：
- 延迟低（秒级或毫秒级）
- 技术复杂度高
- 资源成本较高
- 适合监控、预警等场景

---

### 5.4 数据回溯 (Data Backfill)

**定义**：重新处理历史数据，修复数据问题或变更处理逻辑。

**场景**：
- ETL 逻辑变更，需要重算历史
- 数据质量问题修复
- 新增维度字段需要填充历史值

---

## 六、元数据管理

### 6.1 元数据 (Metadata)

**定义**：描述数据的数据，包括数据的结构、含义、来源、质量等信息。

**元数据分类**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **技术元数据** | 数据的技术属性 | 表结构、字段类型、索引 |
| **业务元数据** | 数据的业务含义 | 字段中文名、业务定义、口径 |
| **操作元数据** | 数据的运行信息 | 更新时间、数据量、执行日志 |

---

### 6.2 数据字典 (Data Dictionary)

**定义**：记录数据结构和定义的规范文档。

**包含内容**：
- 表名和表说明
- 字段名、类型、长度
- 字段中文名和业务含义
- 主键、外键、索引
- 示例值和取值范围

---

### 6.3 数据标准 (Data Standard)

**定义**：统一的数据定义、编码和格式规范。

**标准类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **命名标准** | 表、字段的命名规范 | 表名用下划线分隔 |
| **编码标准** | 业务编码的统一规范 | 客户编码规则 |
| **格式标准** | 数据格式的统一规范 | 日期格式 YYYY-MM-DD |
| **值域标准** | 枚举值的统一定义 | 性别：M/F/U |

---

## 七、指标体系

### 7.1 指标分类

#### 原子指标 (Atomic Metric)

**定义**：最基础、不可再分的度量单位，直接通过聚合函数对明细数据计算得出。

**特点**：
- 不包含任何维度限定条件
- 通常对应单一聚合函数（SUM、COUNT、AVG、MAX、MIN 等）
- 是派生指标和复合指标的计算基础

**示例**：

| 指标名称 | 计算逻辑 | 数据来源 |
|---------|---------|---------|
| 订单总额 | SUM(order_amount) | dwd_order_detail |
| 订单数量 | COUNT(order_id) | dwd_order_detail |
| 用户数 | COUNT(DISTINCT user_id) | dwd_user_behavior |

---

#### 派生指标 (Derived Metric)

**定义**：在原子指标的基础上，增加维度限定条件（时间、地区、业务类型等）后得到的指标。

**特点**：
- 继承原子指标的计算逻辑
- 增加 WHERE 条件限定数据范围
- 业务语义更具体

**示例**：

| 派生指标 | 基于原子指标 | 限定条件 |
|---------|-------------|---------|
| 华东区订单总额 | 订单总额 | region = '华东' |
| 本月新增用户数 | 用户数 | create_date >= 本月1号 |
| 有效订单数量 | 订单数量 | order_status = 'valid' |

**与原子指标的关系**：`派生指标 = 原子指标 + 维度限定条件`

---

#### 复合指标 (Composite Metric)

**定义**：由多个原子指标或派生指标通过四则运算组合而成的指标。

**特点**：
- 需要先计算依赖的指标，再套用公式
- 通常表示比率、均值、增长率等
- 具有更强的业务分析意义

**示例**：

| 复合指标 | 计算公式 | 依赖指标 |
|---------|---------|---------|
| 客单价 | 订单总额 / 订单数量 | 订单总额、订单数量 |
| 毛利率 | (收入 - 成本) / 收入 × 100% | 收入、成本 |
| 用户转化率 | 下单用户数 / 访问用户数 × 100% | 下单用户数、访问用户数 |
| 同比增长率 | (本期值 - 去年同期值) / 去年同期值 × 100% | 本期值、去年同期值 |

---

### 7.2 指标构成要素

#### 口径 (Caliber)

**定义**：指标的计算规则和统计范围的精确定义。

**口径要素**：
- **统计范围**：哪些数据纳入计算
- **计算逻辑**：使用什么聚合函数
- **过滤条件**：排除哪些异常数据
- **时间窗口**：统计的时间范围

**示例**：订单总额口径定义
```
指标名称：订单总额
统计范围：所有已支付订单
计算逻辑：SUM(实付金额)
过滤条件：订单状态 IN ('已支付', '已发货', '已完成')，排除测试订单
时间窗口：自然日（0:00~23:59:59）
```

---

#### 修饰词 (Modifier)

**定义**：对指标进行限定的条件描述，使指标语义更加具体。

**常见修饰词类型**：

| 类型 | 示例 |
|------|------|
| 时间修饰 | 近7天、本月、上季度、年初至今(YTD) |
| 状态修饰 | 有效的、已完成的、进行中的 |
| 对比修饰 | 同比、环比、累计 |
| 范围修饰 | 首次、新增、活跃 |

---

### 7.3 指标管理

#### 指标域 (Metric Domain)

**定义**：指标所属的业务领域分类。

**常见指标域**：

| 指标域 | 包含指标类型 |
|--------|-------------|
| 交易域 | 订单、支付、退款相关指标 |
| 用户域 | 注册、活跃、留存相关指标 |
| 流量域 | PV、UV、访问时长相关指标 |
| 商品域 | 库存、动销、品类相关指标 |
| 财务域 | 收入、成本、利润相关指标 |

---

#### 指标血缘 (Metric Lineage)

**定义**：指标之间的上下游依赖关系。

**血缘类型**：
- **数据血缘**：指标依赖的数据表
- **指标血缘**：复合指标依赖的原子/派生指标

**示例**：
```
dwd_order_detail (数据表)
    └── 订单总额 (原子指标)
            └── 华东区订单总额 (派生指标)
            └── 客单价 (复合指标，同时依赖"订单数量")
```

---

#### 指标目录 (Metric Catalog)

**定义**：对指标进行分类组织的层级结构，便于检索和管理。

**目录结构示例**：
```
指标中心
├── 交易指标
│   ├── 订单指标
│   │   ├── 订单总额
│   │   ├── 订单数量
│   │   └── 客单价
│   └── 支付指标
│       ├── 支付成功率
│       └── 支付金额
├── 用户指标
│   ├── 规模指标
│   │   ├── 注册用户数
│   │   └── 活跃用户数
│   └── 质量指标
│       ├── 用户留存率
│       └── 用户转化率
└── 运营指标
    └── ...
```

---

### 7.4 业务应用指标

#### KPI (关键绩效指标)

**定义**：用于衡量核心业务目标达成情况的关键指标。

**特点**：
- 数量有限（通常 5-10 个）
- 直接关联业务目标
- 有明确的目标值和考核周期

---

#### 北极星指标 (North Star Metric)

**定义**：最能反映产品核心价值的单一指标，是公司战略方向的量化体现。

**特点**：
- 整个公司只有一个
- 能够反映用户获得的核心价值
- 是长期增长的领先指标

**示例**：
- 电商平台：GMV（成交总额）
- 社交产品：DAU（日活跃用户）
- SaaS 产品：MRR（月经常性收入）

---

#### 过程指标 vs 结果指标

| 类型 | 定义 | 示例 |
|------|------|------|
| **过程指标** | 衡量业务过程中间环节的指标 | 访问量、加购数、咨询数 |
| **结果指标** | 衡量最终业务成果的指标 | 成交额、转化率、利润 |

**关系**：过程指标是结果指标的先行指标，优化过程指标通常能带动结果指标提升。
